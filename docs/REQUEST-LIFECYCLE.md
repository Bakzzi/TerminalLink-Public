# 요청 보기: 공통 상태와 전송 구조 개선안

상태: **공통 핵심 모듈 구현·격리 시험 완료, 운영 연결·배포 전** (2026-10-21).
현재 구현 범위, 시험 결과와 남은 전환 조건은 [구현 현황](REQUEST-IMPLEMENTATION-STATUS.md)에 기록한다.
기준 소스: connector `deecd165993bd4a036e0e830c4026b946330bdc2`,
Desktop `d39d956a46a46e8a2d9740f223c2814cee43483f`.
이 문서의 목표 동작을 현재 제품에서 검증한 기능으로 해석하지 않는다.

## 결정

요청의 식별·상태·답장 결과를 PC의 공통 요청 관리자 한 곳에서 관리한다.
Android 팝업, Desktop 팝업, 알림 답장은 그 상태를 표시하고 같은 명령을 보낸다.
대화 전체 재탐색이나 현재 화면의 질문 유무가 요청의 생존 여부를 결정하지 않게 한다.
공식 Codex 요청 프로토콜을 우선 조사하되, 기존 Windows Terminal의 동일한 실행 작업에
간섭 없이 연결되는 것이 확인된 경우에만 사용한다.

기존 창·탭·PowerShell·SSH·Codex를 종료하거나 새 대화로 대체하지 않는다.
기존 작업을 Codex 데스크톱 앱으로 우회시키거나 그 앱의 제어권을 가져오지 않는다.
일반 메시지의 네이티브 전송, 대화 기록 보관, 첨부, 파일함은 이번 변경 범위에서 분리한다.

## 확인된 구조적 문제

아래는 현재 소스에서 확인한 동작이다. 각 항목이 모든 과거 장애의 원인이었다는 뜻은 아니다.

| 경계 | 현재 동작 | 반복 장애가 생길 수 있는 이유 |
| --- | --- | --- |
| 원본 연결 | `NotificationTarget.Connect/Current`가 답장 시 별도 reader와 원본 연결 검사를 수행 | 팝업에서 이미 읽은 요청도 새 연결·화면 비교의 일시 실패로 제출이 막힐 수 있음 |
| 질문 식별 | `NotificationInput.RequirePrompt`가 현재 화면의 질문·선택지 문자열을 다시 대조 | 접기, 줄바꿈, 선택 화면, Codex 표시 형식에 전송이 의존 |
| 모바일 두 경로 | `ActionControls.confirmRecord`는 원본 요청 명령, `choose/confirm`의 네이티브 경로는 UP/DOWN/TAB/text/ENTER를 직접 전송 | 한 기능의 상태·완료 의미가 경로마다 다르고 직접 키 경로는 입력문을 즉시 비움 |
| 복수 질문 | `RecordRequest.first`와 `DesktopTab.Request`가 첫 항목 중심으로 표시 | 팝업을 연 요청과 현재 목록의 첫 요청이 달라지는 상황을 별도로 처리해야 함 |
| 요청 생명주기 | `CodexFeed`가 특정 내부 이벤트·답장 텍스트로 요청을 추가/제거 | 내부 형식의 변화, 불완전한 읽기, 오래된 이벤트와 명시적 완료를 구분할 계약이 부족 |
| 요청 개수 | `CodexFeed`가 32개 초과 시 오래된 대기 질문을 제거 | 아직 유효한 요청이 저장/표시 한도 때문에 사라질 수 있음. 대화 메시지 상한과 별개 |
| 전송 성공 | `NotificationInput.ExecuteCore`는 Enter 직후 `ok=true` | 네이티브 입력 전달과 Codex의 답장 접수 확인이 같은 성공으로 처리됨 |
| 재시도 | `TextRemote`의 nonce 중복 거부, `ConsoleBridge`의 기다리는 작업, 각 UI의 타이머가 따로 존재 | 완료 결과 조회·재접속 복구를 공유하지 않음. 중복 거부만으로 결과를 복원할 수 없음 |
| PC/모바일 공통성 | Desktop은 분리 브랜치의 호스트 소스를 연결하고 모바일은 connector를 사용 | 원격 reader만 고정 출처로 가져오는 현재 방식으로는 요청 처리의 동일 버전을 보장하지 못함 |

기존의 초안 보존, nonce, 소유권 검사 자체를 없애는 변경이 아니다.
그 보호를 화면 비교와 UI별 임시 상태에서 명확한 요청 계약으로 옮기는 변경이다.

## 공식 연동 조사 결과와 한계

참고: [Codex App Server 공식 문서](https://learn.chatgpt.com/docs/app-server).

- 로컬 CLI와 실행 중 daemon의 버전 조회는 모두 `0.163.0`이었다.
- 설치된 CLI에서 `app-server generate-json-schema`를 실행했다. 계정 인증이나 AI 작업 실행은 하지 않았다.
- 생성 규격에는 `item/tool/requestUserInput`, 질문별 `id`, `threadId`, `turnId`, `itemId`,
  질문 ID를 키로 하는 `ToolRequestUserInputResponse.answers`, `serverRequest/resolved`가 있다.
- 설치 규격의 `isBlocking`은 필수이며, 관련 질문 API에는 실험적 표시가 있다.
  웹 문서의 예제만으로 설치 버전의 지원 여부를 판정하지 않는다.
- `thread/resume` 규격은 같은 서버의 실행 중 thread에 다시 합류하는 경우를 설명한다.
  이것만으로 임의의 기존 TUI에 대한 요청 재전달·답장 권한·제어권 보존이 입증되지는 않는다.
- `thread/read`는 기록 조회이지 실시간 요청 구독이나 답장 연결이 아니다.
  `serverRequest/resolved`는 답장뿐 아니라 요청 철회에도 발생하므로 우리 답장의 접수 증거로 단독 사용하지 않는다.
- `app-server proxy`의 control socket은 WebSocket HTTP Upgrade가 필요했다.
  이 handshake를 사용한 실행 중 서버의 읽기 전용 초기화는 성공했다.
- 격리된 App Server·가짜 모델 공급자·실제 시험용 TUI에서 두 질문 묶음, 늦은 연결,
  재접속, 외부 답장, 답장 후 원래 TUI 입력 유지, 철회 알림을 확인했다.
  이는 알려진 시험 thread에 대한 결과이며 임의의 기존 탭 식별이나 SSH 지원의 증거는 아니다.
- 사용자 터미널에는 입력하거나 resume/start/interrupt/소유권 변경 명령을 보내지 않았다.

따라서 공식 API를 곧바로 운영에 적용한다는 결론은 내리지 않는다.
연결 방식의 전환은 아래 단계 A가 통과해야 한다. 새 App Server를 켜서 같은 기록을 읽는 것만으로
기존 TUI의 요청을 제어할 수 있다고 가정해서는 안 된다.

규격 재확인 명령(생성 결과는 Git에 넣지 않음):

```powershell
codex --version
codex app-server daemon version
codex app-server generate-json-schema --out build/request-contract-audit/schema
```

## 목표 계약

### 식별과 상태

논리 요청 키는 `agent instance + threadId + turnId + itemId`를 기준으로 하고, 질문은 그 안의
`questionId`로 구분한다. 같은 문구가 반복되어도 다른 요청이다. 탭 제목, 화면 위치, 첫 항목 순서,
문장 해시만으로 식별하지 않는다. 연결마다 쓰는 JSON-RPC request ID는 논리 요청 ID와 따로 보관한다.
기존 원본의 `call:index` ID도 원본 그대로 보존하고 어댑터에서 논리 요청에 대응시킨다.

탭과 thread의 연결은 명확한 실행 세션 ID와 원본 ID로 유지한다. 클릭할 때마다 처음부터
대화 전체를 비교해 새 연결을 만드는 흐름은 제거한다. 프로세스 수명·SSH 연결·thread가 실제로
바뀌었을 때만 다시 식별한다. 화면에 근거가 안 보이는 것과 실제 신원 변경을 구분한다.
단, 임의의 기존 TUI에서 이 ID 대응을 얻는 방법은 단계 A의 별도 통과 항목이며,
공식 API가 존재한다는 사실만으로 이 문제가 자동 해결됐다고 보지 않는다.

상태는 세 축으로 분리한다.

| 축 | 상태 예시 | 의미 |
| --- | --- | --- |
| 요청 | open / resolved / withdrawn | 질문 자체가 유효한지 |
| 연결 | fresh / stale / unsupported | 지금 서버 상태를 확인할 수 있는지 |
| 답장 | notSent / dispatching / sentUnconfirmed / accepted / rejected | 내 답장이 어디까지 진행됐는지 |

연결 오류는 요청 완료가 아니다. 읽기 실패와 타임아웃으로 질문·선택·초안을 삭제하지 않는다.
동일 요청의 완료/철회 또는 권위 있는 전체 상태의 확인으로만 생명주기를 바꾼다.
완료 후에도 열려 있던 팝업에는 완료 사유를 표시하고, 작성 중인 글은 복사할 수 있게 보존한다.
목록에서 항목이 보이지 않는다는 이유만으로 완료로 처리하지 않는다.

관리자는 `streamEpoch + revision`을 발급하고, snapshot에는 범위와 완전성 여부를 넣는다.
클라이언트는 오래된 revision과 중복 이벤트를 무시하고, 이벤트 누락을 감지하면 상태만 재조회한다.
원본/서버가 바뀌면 기존 초안을 해당 이전 요청에 남겨 두고 새 요청으로 전송하지 않는다.

### 복수 질문과 답장

1. 팝업은 열 때 선택한 요청 ID에 고정한다. 새 질문이 와도 읽는 내용을 교체하지 않는다.
2. 한 요청에 질문이 여러 개면 묶음과 질문별 선택·초안을 모두 보존한다.
   서버가 한 번의 답장 객체를 요구하면 전체 `answers` 맵으로 제출한다.
   개별 전송은 해당 어댑터가 명시적으로 지원할 때만 허용한다.
3. UI는 `requestKey + revision + submissionId + answers`를 관리자에 보낸다.
   관리자만 답장 형식, 현재 요청, 명시적으로 고른 승인 범위를 검증하고 전송한다.
4. 관리자는 요청별 제출을 직렬화하고, 전송 시작 전 submissionId와 payload 해시를 기록한다.
   동일 ID·동일 내용의 재요청은 저장된 상태를 돌려주고, 동일 ID·다른 내용은 거부한다.
5. 앱의 타임아웃/재접속은 submissionId로 결과를 조회한다. 새 nonce를 발급해 무조건 다시 보내지 않는다.
6. 네트워크 쓰기 성공은 접수가 아니다. 해당 답장이 접수된 증거가 있을 때 `accepted`로 바꾸고
   연결된 팝업·알림만 완료 처리한다. 철회만 확인되면 철회로 표시한다.
7. 송신 후 결과가 불명확하면 `sentUnconfirmed`로 보존한다. 서버의 중복 방지나 결과 조회가 보장되지
   않으면 자동 재전송하지 않는다. 이 구간에서 무조건적인 exactly-once를 약속하지 않는다.
8. 터미널에서 직접 답했거나 다른 기기에서 처리했으면 같은 요청의 완료를 전파한다.
   그동안 작성한 초안을 다음 질문으로 옮기지 않는다.

미완료 요청을 32개 같은 고정 상한으로 제거하지 않는다. UI는 필요할 때 페이지로 렌더링하며,
메모리 사용은 원본 보관과 분리한다. 완료 기록과 중복 방지 기록의 정리는 서버 재생 범위·조회 가능 기간을
명시한 정책으로 수행한다. 정리로 과거 요청이 부활하지 않게 기준 revision을 유지한다.

### 배치와 보안

- PC 연결 프로그램의 요청 관리자를 단일 처리 주체로 한다. Desktop은 같은 사용자만 접근 가능한
  로컬 IPC로 연결하고 Android는 기존 인증된 연결을 이용한다. Desktop이 두 번째 휴대폰으로 접속하지 않는다.
  기존 휴대폰 연동의 백그라운드 실행 경계를 사용하며 사용자에게 별도 연결 창을 새로 요구하지 않는다.
- Desktop 브랜치의 폐기 가능성을 유지한다. 로컬 IPC가 없는 connector에서는 현재 버전 동작을 유지하고,
  새 기능으로 전송한 도중 구형 키 입력 경로로 자동 전환하지 않는다.
- 공식 어댑터와 기존 네이티브 어댑터가 하나의 요청 계약을 구현한다. UI에서 별도의 화면 파서를 실행하거나
  UP/DOWN/TAB/ENTER 묶음을 직접 보내는 요청 답장 경로는 전환 완료 후 제거한다.
- 네이티브 어댑터는 기존 세션의 신원·요청 경계를 확인한다. 화면에 의존하는 한계는 남으므로
  공식 프로토콜 경로와 동일한 보장을 표시하지 않는다. 지원하지 않는 형식은 명시적으로 알린다.
- Windows는 기존 사용자 경계와 보호 저장소, Android는 앱 전용 저장소/보호 키를 사용한다.
  비밀 질문은 알림 본문·진단·평문 저장에서 제외한다. 로그에는 내용 대신 단계·상태·비식별 키를 남긴다.
- SSH는 등록된 서버/사용자/호스트 키 경계를 유지한다. 외부에 새로운 App Server 포트를 공개하지 않는다.
  연결된 서버의 Codex 버전과 기능을 별도로 확인하며 로컬 버전의 규격을 강요하지 않는다.
- 기능별 지원 표를 가진다: 요청 읽기, 기존 요청 재전달, 답장, 결과 확인, 그룹 제출, 승인, 재접속.
  알려지지 않은 상태는 거짓 성공이나 완료가 아닌 구체적인 확인 필요 상태로 표시한다.

## 실행 순서와 중단 기준

### A. 기존 세션과 공식 연결의 호환성 입증

별도 시험 프로필에서 기존 TUI와 두 번째 클라이언트를 함께 연결한다.
같은 프로세스·같은 thread로 질문 수신, 두 질문 묶음, 뒤늦은 접속, 연결 끊김, 다른 클라이언트 답장,
승인/철회, UI 소유권 보존을 확인한다. 로컬과 SSH는 각각 검증한다.
질문 이벤트의 실제 delivery 의미와 재접속 시 pending request 재전달 여부를 확인한다.

통과 조건: TUI가 계속 입력 가능하고 동일 요청에 답장이 반영되며 재접속 후 미완료 상태를 복구한다.
새/기존/재개 탭을 실제 thread ID에 연결하는 방법도 확인해야 한다. 짧은 동일 질문이나 화면 문자열만으로
다른 대화를 선택하지 않아야 한다.
미통과 시 원인을 기록하고 운영 전환을 중단한다. 새 대화 생성이나 화면 추측으로 이 검증을 대신하지 않는다.
연결 계약이 없는 구형 환경은 버전별 네이티브 어댑터의 지원 범위를 명시한다.

### B. 공통 관리자와 상태 계약 구현

실제 요청 캡처에서 개인정보를 제거한 이벤트 순서 fixture와 가짜 서버로 상태/중복 방지를 검증한다.
읽기와 표시를 먼저 별도로 관찰하고, 기존 사용자 작업에는 답장하지 않는 비교 모드로 확인한다.
요청별 상태 저장과 로컬 IPC는 이 단계에서 구현한다. 일반 메시지 전송 로직은 바꾸지 않는다.

### C. PC·모바일·알림 동시 연결

Desktop의 독립 요청 판단과 Android의 직접 키 전송을 관리자 명령으로 교체한다.
같은 계약 fixture를 C#과 Android 검사에서 사용한다. capability가 없는 구버전과의 조합을 검사한다.
전환된 요청 하나를 동시에 두 경로가 처리하지 못하게 한다.

### D. 제한된 배포와 회귀 확인

한 시험 탭에서 전체 흐름을 통과한 뒤 기존/새/재개 탭과 로컬/SSH에 동일하게 적용한다.
개별 탭 이름으로 코드 예외를 만들지 않는다. 구현 커밋·규격 버전·검사 결과·배포 파일 해시를 묶는다.
기존 버전은 즉시 복귀 가능하게 보존하고 실패 시 요청 어댑터 전환만 되돌린다.

## 반드시 통과할 재발 방지 사례

| 사례 | 기대 동작 |
| --- | --- |
| 팝업을 읽거나 작성하는 동안 일시 읽기 실패 | 질문·스크롤·선택·초안 유지, 연결 상태만 변경 |
| 같은 문구의 두 요청 / 두 탭 | 서로 다른 ID로 독립 처리 |
| 한 요청에 두 질문 / 동시에 여러 요청 | 모든 질문과 초안 보존, 서버가 요구하는 묶음대로 제출 |
| 새 요청이 먼저 오고 이전 완료가 늦게 도착 | 열려 있는 요청을 다른 질문으로 바꾸거나 새 요청을 닫지 않음 |
| 전송 버튼 연타 / PC·모바일 동시 답장 | 요청별 직렬 처리, 이미 처리된 요청에 추가 쓰기 없음 |
| 답장 전 끊김 / 송신 직후 끊김 / 접수 후 ACK 유실 | 각각 미전송·결과 확인 중·접수됨을 구분, 무조건 재전송 금지 |
| 앱·관리자 재시작 후 같은 submissionId 조회 | 저장된 결과 복원 또는 명시적인 확인 필요, 중복 제출 없음 |
| 터미널에서 직접 답장 / 서버 자동 철회 | 올바른 완료 사유 전파, 초안을 다음 요청에 전송하지 않음 |
| 승인·권한 요청 / 비밀 질문 | 명시적 선택, 범위 보존, 알림/로그에 비밀 누출 없음 |
| 화면 크기·스크롤·제목 애니메이션·접힘 변경 | 공식 경로의 요청 ID·상태·답장에 영향 없음 |
| 새/기존/옛 기록 resume, 로컬/SSH | 같은 계약 적용, 지원되지 않는 환경은 이유와 복구 방법 표시 |
| PID 재사용 / SSH 재접속 / 동일 cwd의 다른 대화 | 이전 대상에 입력하지 않음, 새 세션과 별도로 연결 |
| 부분 snapshot / 이벤트 중복·역순·누락 | 완료 오판·알림 부활 없음, revision 기반 재동기화 |
| 32개보다 많은 미완료 질문 | 살아 있는 요청을 한도 때문에 삭제하지 않음 |
| 구버전 앱·새 connector / 새 앱·구 connector | capability에 맞는 명확한 동작, 전송 도중 경로 변경 없음 |

이 표는 **구현 완료 기준**이며 현재 통과한 검사 목록이 아니다.
공통 핵심 모듈의 43개 검사와 격리 프로토콜 시험은 통과했다.
기존 탭 식별·원격 연결·클라이언트 전환은 아직 미완료이며 운영 프로그램은 교체하지 않았다.
