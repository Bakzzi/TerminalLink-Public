# 반복 가능한 상황 검사

주요 모바일 실기기 대상은 **Galaxy S25**다. Android/One UI 버전은 실기기 확인 때 기록하며 추정하지 않는다.

2026-10-25 검사는 실제 사용자 터미널에 입력하지 않고 운영 코드를 실행한다. Android OS 표면만 JVM 대역으로 바꾸며, PC 요청 상태·저장·IPC와 Desktop 표시 상태는 합성 식별자로 분리한다. 에뮬레이터를 켜지 않고 빌드는 한 번에 하나만 실행한다.

| 상황 | 자동 검사 | 실기기에서 별도 확인 |
| --- | --- | --- |
| Wi-Fi/모바일 데이터 전환, 화면 꺼짐 후 복귀 | 연결 종료·타임아웃·재생성, 순서 변경 64개 고정 시드, 누락 후 재동기화 | S25 실제 망 전환·절전 복귀 지연 |
| 전송 중 탭 전환 | 늦은 성공이 다른 탭/새 초안을 지우지 않음, 중복 ACK·타이머 무시 | 삼성 키보드 열림·닫힘, IME 조합 입력 |
| 새 Codex 대화 | 원본 없이 일반 전송, 원본이 ACK보다 먼저 도착해도 잠긴 초안 정리 | 실제 Windows Terminal/SSH에서 직접 사용 |
| 요청 여러 개 | 32개 시드로 읽기 실패·복구·동시 요청·늦은 결과·재시작 조합 | S25 요청 작성 중 화면 회전·백그라운드 |
| 알림 연속 답장 | 긴 답장·중복 액션·알림 삭제·지연된 푸시·다른 탭 유지 | One UI 알림 답장 UI, 알림 권한·절전 정책 |
| 첨부 | 로컬/원격 파일 capability, 원격 전송 스크립트, 완료 콜백의 탭 구분 | S25 사진·PDF 선택기 및 실제 업로드 |
| Desktop 여러 탭 | 8개 탭 × 32개 시드, 일시 읽기 실패·반복 응답·완료 행 유지 | 실제 글 입력 없이도 가능한 별도 화면 확인 |
| 업데이트 | 전송·초안·팝업이 있으면 보류하는 기존 합성 검사 | S25 설치 확인 요구 여부 |

## 발견하고 수정한 실패

- Android 0.9.50 읽기 실패 표시: 실제 `ReadingView.update/render/sameContent`를 JVM에서 실행한다. 같은 네이티브 탭의 원본 읽기 실패/null 수신, 표 포함 대화, 동일 내용 복구, 새 답변, 다른 탭 및 새 대화를 검사한다. 일시 실패는 본문 `setText`, 표 재생성, 스크롤 복구를 호출하지 않고 별도 입력창 위 안내만 바꿔야 한다. 보관한 내용은 표시 전용이며 원본 의존 입력의 권한으로 사용하지 않는다. Android 레이아웃/삼성 키보드는 실제 기기 확인 전까지 미검증이다.
- 요청의 정상 답장이 대화 압축 후 약 3분 늦게 원본에 기록되는 실제 사례를 확인했다. 기존 60초 결과 조회를 첫 1.5초/이후 5초 간격, 최대 5분으로 변경했다. 원본 접수 확인 전까지 성공이라고 표시하지 않고, 텍스트/Enter는 반복하지 않는다. 실제 팝업 코드에 3분 지연된 접수와 5분 조회 종료를 넣어 최종 assistant 답변 없이 팝업/요청 표시가 종료되는지 검사한다. 이 변경은 Codex 작업을 강제 중단하거나 압축을 생략하지 않는다. 최초 전송 거부의 상세 원인은 기존 저장 기록만으로 확정하지 못했다.

- Connector 0.9.54 / Android 0.9.49 첨부 첫 시도 보완: 같은 실제 콘솔 프레임을 고정하고 입력 없이 실행한 기존 첨부 대상 확인은 첫 시도 7,011ms에 실패하고 두 번째 4,316ms에 성공했다. 최초 대화 목록 준비가 고정 7초보다 오래 걸린 것이 원인이었다. 수정 후 첫 확인 10,722ms에 성공했고 재확인은 20ms였다. 이것은 대화 대상 확인의 실측이며 실제 파일 전송 성공을 뜻하지 않는다.
- 첨부 준비 대기는 전체 30초 안에서 초기 목록 준비와 이후 매칭을 구분한다. 실제 대상 변경·셸 복귀·다른 원본·모호한 근거는 계속 거부한다. PC 응답 대기는 60초, 모바일 로컬 첨부 결과 대기는 90초로 포함 관계를 맞춘다. 준비 중 전송을 취소하거나 텍스트/첨부/Enter를 다시 보내지 않는다.
- `attachment-send` JVM 검사는 실제 `ImageAttachments.send/begin/finish/message`를 실행한다. 사진 3장 및 사진·문서 혼합, 로컬·SSH, 성공·명시적 실패 조합에서 마지막 업로드 완료 응답을 지연시키고, 업로드 전송과 메시지 전달이 겹치지 않는지 확인한다. 전송 버튼을 다시 눌러도 중복 제출하지 않으며, 첫 클릭이 업로드 완료 뒤 자동으로 메시지 전달까지 이어져야 한다. 네트워크 상대·OS 화면은 대역이다.

- Android 0.9.48 요청 완료 보완: 기존 팝업 검사는 성공 ACK 뒤에도 `expanded && recordEnded`를 정상으로 인정했다. 실제로는 답변이 원본에 도착해도 팝업에 종료 안내가 남고, 뒤의 요청 표시도 다음 답변까지 유지되는 잘못된 기대였다. 신규 완료 흐름 검사를 이전 팝업 코드에 실행하면 실패한다.
- 새 검사는 `전송 → 원본 요청 목록 비움/ACK 순서 교차 → 팝업 닫힘 → 요청 표시·알림 제거`를 연결하며, 후속 assistant 최종 답변을 주지 않는다. 오래된 원본·터미널 큐·Action Required 제목, 다른 탭, 서비스 재생성, 같은 문구의 새 요청, 두 질문 중 하나의 완료, 외부에서 끝난 미전송 초안도 검사한다. 지연된 이벤트 snapshot과 백그라운드 푸시도 같은 완료 표시를 사용하며 별도 재현 검사로 확인한다. OS 창/알림 표면은 JVM 대역이다.
- 확인된 요청 식별자는 PC 등록·네이티브 탭·원본 대화·질문별로 구분하고 해시만 보관한다. 완료한 질문만 표시 목록에서 제외하며 원본 대화는 변경하지 않는다. 네이티브 탭이 닫히거나 등록 PC가 바뀌면 관련 상태를 정리한다.
- 전송 미확인 상태는 최대 60초 동안 1.5초 간격으로 기존 제출 결과만 조회한다. 텍스트와 Enter를 다시 보내지 않으며, 기한 뒤에는 초안과 수동 결과 확인을 남긴다. 늦은 성공도 같은 제출에만 적용한다. Galaxy S25 설치·팝업 닫힘·키보드 전환은 실기기 확인 전까지 미검증이다.

- 0.9.53 입력 경로 보완: 앞선 첨부 검사는 `draft` 콜백을 성공 대역으로 바꿔 실제 입력칸 판독을 검사하지 않았다. 사용자 제보 뒤 읽기 전용 관찰에서 현재 입력칸은 `»`(U+00BB), 이전 검사는 `›`(U+203A)만 허용함을 확인했다. 실제 첫 시도 실패를 놓친 검사 공백이다.
- 일반 글은 `NativeMessageInput.Execute → OrderedNativeInput.Send → ConsoleNative.Write`를 사용하며 터미널 키도 같은 순차 처리에 들어간다. 화면/원본을 읽지 않는다. 합성 검사는 두 진입점의 명령 순서·한글/줄바꿈·Enter 1회·OS 쓰기 실패·선택한 프로세스 종료를 비교한다. 실제 사용자 입력을 지우거나 자동 재전송하지 않는다.
- 첨부는 로컬/SSH 모두 `ImageInput.Deliver → WaitDraft → EmptyMain/CheckDraft`를 연결해 검사한다. 양쪽 기호, 첫 읽기/붙여넣기 뒤 재그리기, 이미지+문서+설명, 연속 2회 전송, 실제 기존 초안과 영구 읽기 실패를 포함한다. 바뀌는 화면의 읽기만 재시도하고 파일/설명/Enter는 재전송하지 않는다. 새 대화와 알림 답장의 입력칸 판독에도 두 기호를 적용한다.
- 이 검사는 Win32·Codex·S25 전체를 대체하지 않는다. 실제 폰 전송은 별도 검증 상태로 기록한다. 앞선 JVM 이벤트/알림 검사 통과를 실제 입력 경로 성공으로 보고하지 않는다.

- 이벤트 사이가 빠졌는데도 수신 커서를 앞으로 넘기던 문제: 빠진 위치에서 다시 요청한다. 중복 재동기화 요청은 합친다. 오래된 snapshot과 불완전한 payload는 현재 상태를 덮지 않는다.
- 늦은 전송 성공이 다른 탭 또는 타임아웃 뒤 새로 작성한 동일 문구를 지우던 문제: 잠긴 전송의 현재 탭에서만 입력을 비운다. 타임아웃 뒤 도착한 성공은 현재 초안을 지우지 않는다. 첨부 완료도 동일한 콜백을 사용한다.
- 업데이트 설명에 한글이 있을 때 Windows PowerShell의 기본 코드 페이지로 UTF-8 목록을 읽어 다음 게시가 실패하던 문제: 게시기가 이전 목록을 명시적으로 UTF-8로 읽는다. 실제 게시 단계에서 확인했다.

## 실행과 중단 기준

`tools/test-mobile-scenarios.ps1`는 실제 요청 팝업·알림·메시지 전송 코드와 상황 검사를 순차 실행한다. JSON 의존성은 기존 `tools/test.ps1`에서 받은 고정 해시 파일을 재사용하며 각 Java 실행은 최대 128MB 힙을 사용한다.

`tests/request-lifecycle/check.ps1`는 요청 상태와 재시작/IPC 조합을 검사한다. 두 검사는 기존 `tools/test.ps1`에도 포함된다. Desktop의 `StateScenarioChecks`는 별도 브랜치의 `--self-check`에 포함된다.

검사가 실패하면 해당 실패를 고친 뒤 영향받은 검사를 다시 실행한다. 모두 통과하면 동일 검사를 이유 없이 반복하지 않는다. 합성 검사 통과, APK 게시, 휴대폰 설치, S25 실제 동작 확인을 각각 구분한다. 이 검사는 모든 Codex/One UI 동작에 대한 무결점 보증이 아니다.
